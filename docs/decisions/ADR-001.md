# ADR-001: Preserve Request Status History

## Problem

Employees need to track the current status of their requests.
Storing only the current status would make current-state queries simple,
but would provide no record of how the request status changed over time.

## Options

### Option 1 — Store only the current status
Simple to query, but previous request states are lost.

### Option 2 — Store status events only
Preserves complete history, but finding the current status requires
reading the latest event.

### Option 3 — Store current status and status events
Keeps current-state queries simple while also preserving status history.

## Decision

Store both `Request.current_status` and `RequestStatusEvent`.

This keeps current-status queries simple while preserving a record
of status changes for traceability.

## Consequences

The current status is simple to query and the status history remains
available.

The trade-off is slightly more stored data, and the system must keep
`Request.current_status` consistent with the latest `RequestStatusEvent`.

The current status update and corresponding status event must be saved
as one consistent operation.
